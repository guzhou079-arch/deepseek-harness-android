# 手机设置页 · 可执行审美规则

用途：写设置页 / 偏好面板 / 分组列表时的硬约束。每条都能直接写成 CSS，或直接当验收标准。

来源分三类，文内标了可信度：
- **[文档]** Apple HIG / Material 3 官方文档原文（本地缓存在 `.work/design-src/HIG-*.md`）
- **[实测]** 对 iOS 设置页与主流 App 的尺寸观察，非官方数字，按起点值用
- **[推断]** 由文档条款推出的比例关系，落地后要用真机复核

## 一、四个问题，一句话答案

**1. 一张大卡还是多张小卡？**
一屏只准有一张「要被读的物件卡」（账号 / 余额 / 当前主机），且高度 ≤ 屏高 25%；其余全部拆成 2–6 行的小组卡。
—— 依据：iOS 设置首屏只有 Apple ID 一行大卡，其余全是分组小卡；HIG 明确「尽量减少设置项、能用默认值就别问」。设置页的首屏职责是"找到入口"，不是"展示状态"。**[文档 + 实测]**

**2. 行高与行距有数字吗？**
行高 ≥ 48dp（iOS ≥ 44pt，HIG 明文）；行内主文字 15–16sp，单行行高 = 字号 × 1.3；组内行与行之间**不加 gap**，用 1px 分隔线；组间空隙 = 行高 × 0.5–0.7，即 24–34dp。
—— 依据：HIG 可点区域 44×44pt；HIG 字体表 Body 17/22（1.29）、Subhead 15/20（1.33）、Footnote 13/18（1.38），即 1.3 是苹果自己用的行高比。**[文档]**

**3. 图标是装饰还是导航？**
是导航锚点，不是装饰：有就整套有（同 24 画框、同 1.5dp 线宽），且**每行必须有文字标签**，图标永远不单独承义。
—— 依据：HIG Icons 要求「统一尺寸 / 细节量 / 线宽 / 透视」，并与相邻文字同字重；图标的作用是用「熟悉的隐喻」让人一眼认出干什么。**[文档]**
没有图标的代价：行左沿失去锚点，扫视只能靠文字首字，长列表找项变慢；但**只给一半行加图标比全不加更糟**（左沿不齐 = 没有网格）。

**4. 深浅两套怎么保证同一套观感？**
用同一套 L\* 明度阶梯，只换明度，不换分层手段：底 → 卡 → 浮层三级各差 3–5 级；分隔线 = 卡色的 ±8–10 级；文字主/次/三级之间 L\* 差 ≥ 20。色相与饱和度两套差 ≤ 2 级。
—— 依据：HIG 要求每个自定颜色都提供浅/深/高对比三套变体且**语义不变**；M3 用 surface-container 色阶角色分层，同一角色在明暗主题只换 tone。**[文档]**
反过来说：深色靠描边分层、浅色靠底色分层，两套就不是同一套观感，切主题像换了个产品。

## 二、规则清单（可直接抄）

| # | 规则（能写进 CSS 的话） | 依据 | 反例（我们现在的做法） |
|---|---|---|---|
| 1 | 一屏最多一张「阅读卡」，位于首屏顶部，`max-height:25vh` | iOS 设置首屏；HIG「减少设置项」 | 账号 + 余额 + 引擎状态堆成一张大卡，首屏四成高度用来"看" |
| 2 | 组间距 ≥ 组内行距的 2.5 倍：组内 0（靠分隔线），组间 `margin:24px 0` | 眼睛靠**间距**判归属，不靠线；HIG：用留白/容器形状/分隔线表达关系 | 组内 `gap:8px`、组间也 `gap:8px`，比例 1:1，只能靠描边猜分组 |
| 3 | 组内行不用 gap，用 `border-bottom:1px solid` 分隔，且左右缩进到文字左沿 | iOS 列表分隔线缩进到文字起始；HIG「对齐 = 同类」 | 全用 gap 堆，没有分隔线，行与行之间没有"路径感" |
| 4 | 行高 `min-height:48px`；单行 ≤ 2 行文字时 ≤ 64px；主文字 15–16px | HIG 44×44pt；Android 48dp 触区惯例 | 行内 `padding:16px` 撑高但无下限，密的地方挤到 40px 以下 |
| 5 | 同屏字号 ≤ 3 档（16/13/11 或 15/13/12），相邻档差 ≥ 2px；层级靠明度和间距，不靠 1px 字号差 | HIG 字体表：一屏只用 3–4 个文本样式 | 现有 12/13/14/15/16 五档混用，12 与 13 差 1px，肉眼分辨不出，等于噪声 |
| 6 | 圆角只准三档：卡 12–16 / 行内小块 8 / 全屏面板 28，同屏不许出现第四种 | HIG：控件与容器形状要成体系 | 实测同屏出现 28(panel) / 16(卡) / 9(按钮) / 8，且 16→28 之间没有中间层，层级是跳的 |
| 7 | 描边宽度全局二选一（0.5px 或 1px），深色 `rgba(255,255,255,.08–.10)`，浅色 `rgba(0,0,0,.06–.08)` | HIG 高对比要求：同一元素在明暗两套里必须"同样显眼" | 同一张卡三种写法：token 的 16px+0.5px 描边、手写的 16px+1px、smart-search hero 又一套 |
| 8 | 列表行统一左沿：图标 24 画框 + 12 间距 → 文字从 36px 起；无图标行也从 36px 起 | HIG：对齐使同类成立，缩进表达从属 | 有图标的行文字从 52px 起、无图标的从 16px 起，左沿一条线变两条 |
| 9 | 状态用「右侧值 + 文字色」两处表达，不用彩色图标底/彩色胶囊 | HIG：颜色不是唯一承义手段（色盲）；也反对用颜色替代文字 | 彩色图标底 + 状态胶囊 + 描边，三处同时在喊，视线抢不过主操作 |
| 10 | 每屏最多 2 个强调色触点（主操作 + 当前选中） | HIG「谨慎用色」：颜色一多，控件标签就难读 | 品牌色同时出现在图标底、开关、链接、余额数字上 |
| 11 | 深色底 `L* ≥ 6`（不用纯黑），浅色底 `L* 95–97`（不用纯白） | HIG 深色模式：纯黑让层级没地方落 | 深色渐变底 L\*7.2 合规，但卡片只比底高 3 级，靠白描边才看得见 —— 分层手段和浅色不一致 |
| 12 | 间距只用 4 的倍数七档：4 / 8 / 12 / 16 / 24 / 32 / 48 | 8pt 栅格惯例；HIG 布局对齐 | 现在 22px、9px 这类值零散出现，栅格是假的 |

## 三、我们现在这版，哪几处是硬伤

按「改一处就能见效」排序，全部有本地证据。

1. **「同一张卡」有三种写法** —— `.work/l3/token-census.md` 里扫出：走 token 的卡是 16px 圆角 + 0.5px 描边，原型表手写 16px + 1px 描边，smart-search 的 hero 又是自己一套。差 0.5px 描边、差一圈圆角，同一屏里就是两档深浅；观感上「不整齐」的根因在这儿，不在配色。**先统一卡片的三种写法，再谈好不好看。**

2. **组间距 = 组内行距（都 8px）** —— `dsh-client-ui-settings-general` 里 `gap:8px` 出现 7 次、`gap:4px` 4 次，组内组间共用一套值。眼睛判归属靠间距比，1:1 就等于没分组，用户只能靠描边数分组。**这一条改完，设置页立刻"有条理"：组内 0（分隔线）、组间 24。**

3. **字号五档，靠 1px 差分层** —— 12/13/14/15/16 并存。12 和 13 只差 1px，人眼在 3x 屏上分不出档，只感到"字忽大忽小"。**砍到三档（16 主 / 13 副 / 11 注），层级交给明度和间距。**

4. **首屏是一张"要看"的卡，不是"要找"的入口** —— 账号 + 余额 + 引擎状态三合一，首屏四成高度是状态展示，真正的设置入口要滚。**按规则 1 拆：大卡只留账号一行（进账号页），余额和引擎状态降级成组内一行文字。**

5. **深浅两套的分层手段不一致** —— 深色卡靠 `rgba(255,255,255,.08)` 描边浮起来，浅色卡靠底色差浮起来；两套观感是"两套机制"，切主题必然像换产品。**统一成 L\* 阶梯：卡比底亮 3–5 级，两套都用同一个差值。**

6. **圆角层级断层** —— 面板 28 / 卡 16 / 按钮 9 / 小块 8。28 到 16 之间没有中间层，看起来像"大壳里直接塞小方块"。**补一档 20 给组容器，或者把面板降到 20。**

## 四、来源与可信度

- Apple HIG：`layout`、`settings`、`typography`、`color`、`icons`、`accessibility`（.md 原文，本地 `.work/design-src/HIG-*.md`）。44×44pt 出自 accessibility；1.29/1.33/1.38 行高比出自 typography 字体表。
- Material 3 Expressive（m3.material.io）：官网正文由 JS 渲染，本轮**未取到原文**，只用其公开的分层思路（tonal surface 角色 + 形状/色彩表达），不引用具体数值；需要数值时另开一轮抓文档。
- 顶级 App 设置页（Linear / Arc / Things / Raycast / Notion / Vercel）：本轮只有零星抓取，**不作为依据**，规则里没有一条靠它们的像素数成立。
- 带 [实测] / [推断] 的条目是观察与推导，落地按起点值用，真机复核后再写死。
